# Rencana rekonsiliasi database development SA-LMS

Dokumen ini adalah rencana pemeriksaan dan perubahan untuk ditinjau; **tidak ada migration atau perubahan database yang dijalankan**. Jangan menjalankan `prisma migrate dev`, `db push`, seed, atau reset sebagai langkah pemulihan otomatis.

## Bukti pemeriksaan 27 November 2026

- Koneksi baca saja menggunakan konfigurasi `apps/api/.env` mengarah ke PostgreSQL lokal, database `lms`, schema `public`, port `5432`. Identitas target efektif proses API yang sedang berjalan dan statusnya sebagai development masih harus dikonfirmasi oleh pemilik; konfigurasi proses dapat berbeda dari file tersebut.
- Riwayat `_prisma_migrations` pada target yang diperiksa berakhir pada `20260910095944`. Dua migration `20261031021545` dan `20261031024238` berisi SQL identik untuk membuat `referral_codes`; keduanya belum tercatat di target tersebut. Migration `20261031023418_create_referral_codes_table` kosong. Menjalankan seluruh migration begitu saja akan mencoba membuat tabel yang sama dua kali.
- Empat checksum file kerja berbeda pada pembacaan byte langsung, tetapi cocok dengan checksum database setelah normalisasi CRLF ke LF. Konfirmasi pengaturan line ending dan checksum migration di lingkungan pelaksanaan sebelum mengubah riwayat.
- Metadata menunjukkan tidak ada `academic_years.institution_id`, `Departments.institution_id`, `students.referral_code`, `students.referral_expires_at`, `guardians.institution_id`, `attendance_statuses.institution_id`, `attendance_statuses.color`, `attendance_statuses.icon`, dan tabel `referral_codes`.
- Repository membaca kolom tersebut dan menghasilkan Prisma `P2022` (PostgreSQL `42703`) pada endpoint yang terdampak. Tidak ada perubahan database dalam pemeriksaan ini.
- Pada saat pemeriksaan, tabel tahun ajaran, departemen, siswa, wali, dan status kehadiran masing-masing memiliki nol baris; `institutions` memiliki satu baris. Hitungan ini bukan jaminan untuk saat pelaksanaan atau database lain.

## Rencana sebelum persetujuan

1. Pemilik memastikan database yang benar adalah **development**, termasuk host, port, database, schema dan identitas proses API yang memakainya. Jangan mencetak URL database, kata sandi, atau token.
2. Ambil backup yang dapat dipulihkan, uji pemulihan pada salinan terisolasi, dan hentikan penulisan selama pemeriksaan dan perubahan. Bandingkan ulang schema, row count, constraint, indeks, riwayat migration, checksum, dan migration yang belum diterapkan. Periksa juga migration yang berisi perubahan data; jangan menjalankan seed.
3. Tinjau migration yang tertunda secara berurutan, termasuk foreign key pada `20260921004300`, `20261009094630`, dan perubahan foreign key `20261026142922`. Validasi keberadaan constraint dan integritas data sebelum menetapkannya. Jangan menganggap metadata Prisma saja sebagai bukti bahwa perubahan fisik telah diterapkan.
4. Sepakati penanganan duplikasi `referral_codes` untuk **semua lingkungan**, setelah memeriksa apakah salah satu atau kedua migration telah diterapkan di lingkungan lain. Jangan menghapus atau mengedit migration yang sudah diterapkan secara sepihak. Salah satu pendekatan yang perlu ditinjau adalah menerapkan migration pertama dan merekonsiliasi catatan migration duplikat hanya setelah membuktikan definisi tabel, indeks, foreign key, dan checksum sesuai. Setiap langkah perubahan riwayat memerlukan persetujuan eksplisit; jangan menandai migration sebagai selesai untuk menyembunyikan drift.
5. Tinjau perubahan minimum untuk sembilan ketidakcocokan di atas beserta semua perbedaan schema lainnya. `20261105000000_add_institution_id_to_attendance_statuses` sengaja gagal bila terdapat status lama: jika ada data, tentukan pemetaan institusi berdasarkan bukti dan persetujuan pemilik, bukan institusi tebakan. Kolom institusi nullable pada tahun ajaran, departemen, dan wali juga memerlukan rencana pemetaan agar data lama tidak hilang dari hasil yang dibatasi institusi.
6. Uji rangkaian yang disepakati pada salinan hasil restore, tanpa seed. Periksa konsistensi foreign key, indeks, izin, jumlah data, dan pembacaan sesuai batas institusi. Simpan urutan tindakan, pemeriksaan sebelum/sesudah, serta rencana rollback berbasis backup untuk ditinjau.
7. Setelah target, backup, hasil uji salinan, dan perubahan spesifik disetujui, operator dapat melaksanakan prosedur yang disetujui. Jangan menjalankan rangkaian migration yang belum diperbaiki secara membabi buta.
8. Sesudahnya verifikasi ulang drift, riwayat migration, dan endpoint dengan sesi terautentikasi yang sah. Jangan menyimpan atau melaporkan token. Pastikan login, batas institusi, HTTP status, filter, tabel, statistik, dan error frontend bekerja dengan data nyata. Record count nol bukan bukti bahwa rendering data berhasil.

## Temuan backend terpisah

`assignmentSubmissionSelect` sebelumnya memilih seluruh `grader` dari model `Users`, yang mencakup hash password dan access token. Setelah persetujuan pengguna, select dibatasi ke ID dan email, dengan tes repository untuk daftar dan detail. Verifikasi respons HTTP aktual masih diperlukan setelah database tersedia dan server memakai build terbaru. Pembatasan akses lintas institusi perlu ditinjau secara terpisah; perubahan ini tidak menambah atau mengubah scoping.

## Hasil latihan pada salinan, 27 November 2026

- Backup PostgreSQL berformat custom telah dibuat dan diperiksa dengan `pg_restore --list`, lalu dipulihkan ke database terpisah `lms_reconcile_d28fdde191` pada server PostgreSQL lokal yang sama. Backup disimpan di direktori sementara `sa-lms-reconcile-21JIXu`. Ini isolasi tingkat database, bukan server terpisah. Saat dibandingkan setelah restore, hitungan pada 47 tabel dan jumlah migration selesai sama dengan sumber.
- Pada salinan saja, SQL migration yang tertunda dijalankan satu per satu dalam transaksi, lalu masing-masing dicatat dengan `prisma migrate resolve --applied`. Setelah migration pertama pembuat `referral_codes`, SQL migration duplikat dibandingkan byte demi byte dan keberadaan nama kolom, indeks, dan constraint diperiksa. SQL duplikat tidak dijalankan; catatan duplikat ditambahkan dengan Prisma setelah pemeriksaan tersebut. Migration kosong juga dicatat. Pemeriksaan ini belum membuktikan seluruh definisi tipe kolom, ekspresi indeks dan aksi foreign key identik; itu tetap harus divalidasi sebelum perubahan di sumber.
- Status Prisma pada salinan menunjukkan 44 migration dan `Database schema is up to date`; `prisma migrate diff --from-config-datasource --to-schema src/prisma --exit-code` juga melaporkan `No difference detected`. Perbandingan metadata menemukan nol tabel atau kolom scalar Prisma yang hilang. Query repository untuk tahun ajaran, departemen, siswa, modul, kelas-mata pelajaran, pengumpulan tugas, KRS dan nilai berhasil dijalankan, semuanya mengembalikan nol baris pada salinan. Prisma diff tidak membuktikan kesesuaian fitur database yang tidak direpresentasikan Prisma atau keamanan data dan akses aplikasi.
- Latihan ini bukan persetujuan perubahan pada sumber dan bukan bukti untuk data yang tidak ada pada salinan. SQL dan `migrate resolve` merupakan dua langkah terpisah; kegagalan di antaranya membutuhkan rekonsiliasi manual, bukan pengulangan membabi buta. Validasi definisi tabel dan constraint, bukti integritas backup, serta persetujuan prosedur spesifik tetap diperlukan sebelum pelaksanaan pada `lms`.

Urutan yang diuji pada salinan adalah `20260921004300`, `20261009094630`, `20261012000000_add_institution_id_to_guardians`, `20261014000000_add_referral_code_and_expires_at_to_students`, `20261021000000_add_institution_id_to_departments`, `20261026142922`, `20261031021545`, `20261031023418_create_referral_codes_table` (kosong), `20261031024238` (duplikat), `20261105000000_add_institution_id_to_attendance_statuses`, lalu `20261112000000_add_color_and_icon_to_attendance_statuses`. Untuk setiap migration nonduplikat, SQL yang ada dijalankan dalam transaksi di salinan, lalu Prisma mencatatnya dengan `migrate resolve --applied`. Untuk duplikat, setelah hash SQL sama dan nama objek diperiksa, hanya langkah pencatatan dilakukan. Jangan menjalankan SQL yang sama dua kali dan jangan menandai migration apa pun tanpa membuktikan efeknya. Prosedur pada sumber harus diperbarui berdasarkan kondisi terkini dan disetujui terlebih dahulu.

## Kandidat transaksi atomik untuk ditinjau

**Digantikan oleh prosedur Prisma resmi di bawah.** Prototipe ini menulis langsung ke tabel internal Prisma dan tidak boleh dipakai pada database asli tanpa persetujuan khusus. Prosedur baru tidak memerlukan penulisan langsung tersebut.

- Identitas environment proses API aktif diperiksa: host `localhost`, port `5432`, database `lms`. Database asli masih memiliki 33 migration selesai, tidak ada migration gagal, dan objek sentinel yang semula hilang masih belum ada.
- Backup baru `sa-lms-atomic-ee15abab73ae/lms.backup` telah dibuat, diverifikasi sebagai arsip, dan dipulihkan ke `lms_atomic_2fcdafb619`. SHA-256: `dd696ec3d8e6d5a97850fe0fb6b8da5e6c069e49cb2aa430ae748ab7ad985f00`. ACL backup hanya memberi akses ke akun Windows pemilik, SYSTEM, dan Administrators. Backup lama juga telah dibatasi ACL-nya. Backup ini mengandung data sensitif dan lokasinya bersifat sementara; ambil backup baru dan uji pemulihan lagi saat jendela pelaksanaan.
- [reconcile-development-clone.cjs](./reconcile-development-clone.cjs) adalah prototipe yang hanya menerima nama database salinan `lms_atomic_*` dan menolak `lms`. Ia memeriksa identitas target, riwayat dan checksum, mengunci tabel, menghentikan proses jika lima tabel terkait tidak kosong, menjalankan SQL yang disetujui, dan mencatat checksum pada `_prisma_migrations` dalam **satu transaksi PostgreSQL**. SQL duplikat dilewati hanya setelah checksum kedua file cocok dan tabel pertama ada.
- Kegagalan disengaja setelah SQL dan catatan sebagian migration menghasilkan rollback: riwayat kembali 33 dan objek yang semula tidak ada tetap tidak ada. Pelaksanaan ulang pada salinan berhasil; Prisma status menunjukkan 44 migration dan Prisma diff tidak menemukan perbedaan.
- Pencatatan langsung ke tabel internal Prisma adalah pendekatan **nonstandar**, berbeda dari `prisma migrate resolve`. Meski uji salinan dan Prisma status berhasil, kompatibilitas internal Prisma dan penanganan hasil COMMIT yang tidak diketahui akibat putus koneksi harus ditinjau sebelum menyetujui penerapan asli. Setelah koneksi terputus, jangan ulangi buta: hubungkan kembali dan periksa schema dan riwayat untuk menentukan apakah transaksi commit seluruhnya atau rollback seluruhnya. Jika hasil parsial atau drift lain ditemukan, hentikan dan gunakan prosedur pemulihan yang disetujui; jangan menimpa data dengan restore tanpa persetujuan.
- Untuk target asli, hentikan semua penulis, buat dan uji restore backup terbaru, ulangi pemeriksaan identitas dan precondition, verifikasi definisi referral serta histori dari lingkungan lain, lalu minta persetujuan untuk penerapan yang menyebutkan secara eksplisit perubahan schema dan penulisan 11 catatan migration. Skrip salinan belum dapat dijalankan terhadap sumber dan memerlukan perubahan terpisah setelah persetujuan. Data pada lima tabel terkait harus tetap nol atau proses berhenti untuk peninjauan pemetaan institusi.

## Prosedur Prisma resmi yang diuji pada salinan

Pada 27 November 2026 backup dengan SHA-256 `dd696ec3d8e6d5a97850fe0fb6b8da5e6c069e49cb2aa430ae748ab7ad985f00` dipulihkan ke database salinan `lms_prisma_4dc68b590d`. Prosedur berikut hanya diuji pada salinan; belum ada persetujuan atau penerapan pada `lms` asli. Perintah dijalankan dari konteks konfigurasi Prisma package `@repo/shared`, dengan URL datasource ditetapkan secara khusus ke salinan tanpa mencetak kredensial.

1. `prisma migrate deploy` menerapkan delapan migration dari `20260921004300` sampai `20261031023418_create_referral_codes_table`, lalu berhenti pada `20261031024238` dengan `P3018` dan PostgreSQL `42P07` karena tabel `referral_codes` telah dibuat oleh `20261031021545`. Ini adalah kegagalan yang diperkirakan **khusus pada kondisi yang diperiksa**, bukan izin untuk mengabaikan error lain.
2. Sebelum resolve, diverifikasi bahwa migration pertama tercatat selesai, migration kedua tercatat gagal dengan `42P07`, dan kedua file SQL identik byte demi byte. Dua belas definisi kolom, sepuluh constraint, empat indeks, dan trigger tabel dibandingkan dengan salinan yang sudah direkonsiliasi; semuanya sama. Definisi juga diverifikasi terhadap schema saat Prisma diff setelah semua migration selesai. Hentikan jika ada perbedaan.
3. `prisma migrate resolve --applied 20261031024238` dijalankan pada salinan untuk menyelesaikan migration gagal, karena efek SQL identik sudah diterapkan oleh migration pertama. Prisma mencatat satu entri percobaan yang di-rollback dan satu entri selesai; hal ini dihasilkan oleh Prisma, bukan penulisan langsung oleh skrip.
4. `prisma migrate deploy` dijalankan lagi dan menerapkan `20261105000000_add_institution_id_to_attendance_statuses` dan `20261112000000_add_color_and_icon_to_attendance_statuses`. Status menunjukkan 44 migration selesai, nol gagal yang belum diatasi, dan satu entri gagal historis yang di-rollback; `prisma migrate status` melaporkan up to date dan `prisma migrate diff --from-config-datasource --to-schema src/prisma --exit-code` melaporkan tidak ada perbedaan.
5. Isi 47 tabel data dibandingkan dengan salinan lain yang dipulihkan dari backup yang sama menggunakan hitungan dan fingerprint seluruh baris; tidak ada perbedaan. Delapan query repository terkait berhasil, dengan nol baris pada tabel yang diuji. Ini tidak membuktikan UI dengan data nyata atau setiap properti PostgreSQL yang tidak diwakili Prisma.

### Langkah minimum yang diusulkan untuk `localhost:5432/lms`

- Minta persetujuan eksplisit sebelum mengubah database asli. Tepat sebelum pelaksanaan, hentikan penulis termasuk API dan worker/scheduler yang dapat menulis, pastikan proses dan datasource benar, buat backup terbaru dengan ACL terbatas dan uji restore pada database terpisah. Ulangi pemeriksaan data, constraint, indeks, checksum dan histori; hentikan jika kondisi berubah atau terdapat baris status kehadiran yang memerlukan pemetaan institusi.
- Jalankan `prisma migrate deploy` dengan datasource yang diverifikasi. Hentikan jika gagal di titik lain atau kode selain `P3018`/`42P07` pada `20261031024238`. Jangan menjalankan reset, seed, `db push`, atau mengedit SQL migration tim.
- Periksa definisi dan status seperti langkah 2 di atas. Hanya jika efek SQL duplikat benar-benar telah terwujud dan sesuai, jalankan `prisma migrate resolve --applied 20261031024238`; kemudian jalankan kembali `prisma migrate deploy`. Jangan menulis langsung ke `_prisma_migrations`.
- Jika terputus atau timbul kegagalan lain, jangan mengulang langkah secara buta. Periksa `migrate status`, catatan kegagalan Prisma dan schema aktual; ikuti [panduan pemulihan Prisma](https://www.prisma.io/docs/orm/v7/prisma-migrate/workflows/patching-and-hotfixing). Jangan melakukan restore yang menimpa database asli tanpa persetujuan pemilik. Prisma deploy menerapkan beberapa migration secara bertahap, sehingga alur ini tidak menjamin seluruh rangkaian bersifat satu transaksi.
- Setelah sukses, bandingkan status, diff, hitungan dan integritas data dengan baseline, restart API, dan uji endpoint secara terautentikasi serta tampilan/filter. Tinjau scoping institusi secara khusus bila data lama ada.

`prisma migrate deploy` berhenti pada `20261031024238` dengan `P3018`/`42P07` seperti latihan. Sebelum resolve, SQL duplikat, status migration pertama dan kedua, serta definisi 12 kolom, 10 constraint, empat indeks, dan trigger dibandingkan dengan salinan resmi; semuanya cocok. `prisma migrate resolve --applied 20261031024238` dan `prisma migrate deploy` berikutnya berhasil. Tidak ada penulisan langsung pada tabel internal Prisma. Status menunjukkan 44 migration selesai, nol gagal yang belum ditangani, dan satu entri historis di-rollback; Prisma diff tidak menemukan perbedaan. Setelah penerapan, fingerprint 46 tabel data yang sudah ada sebelum perubahan cocok dengan backup. Delapan query repository yang sebelumnya diperiksa berhasil, dengan nol baris pada tabel terkait. Layanan pengembangan dinyalakan kembali. Verifikasi HTTP dengan sesi sah dan tampilan tetap diperlukan.
